# Redis 持久化机制核心笔记 (RDB 与 AOF)

## 一、 RDB 持久化 (Redis DataBase)

### 1. 核心概念
在指定的时间间隔内，将内存中的数据集快照（Snapshot）写入磁盘。恢复时，是将这个高度压缩的二进制快照文件直接读回到内存里。
* **文件名称：** `dump.rdb`
* **保存路径：** 默认在 Redis 启动的当前工作目录下。

### 2. 持久化工作流程 (bgsave)
1. Redis 主进程会 `fork` 出一个子进程来进行持久化。
2. 子进程先将数据写入到一个**临时文件**中。
3. 待整个快照写入过程结束后，再用这个临时文件**替换**上次持久化好的旧 RDB 文件。
* **特性：** 整个过程中，主进程不进行任何磁盘 I/O 操作，确保了极高的读写性能。

### 3. 触发策略
* **自动触发：**
  在 `redis.conf` 中配置 `save m n`，含义是：在 `m` 秒内，如果 Redis 数据至少发生了 `n` 次修改，就自动执行 `BGSAVE`。
* **手动触发：**
  * `save`：会**严重阻塞**当前 Redis 服务器的主线程，直到持久化完成，**线上生产环境严禁使用**。
  * `bgsave`：异步触发，会 `fork` 一个子进程负责持久化，主进程只在 `fork` 发生的那一瞬间产生极其短暂的阻塞。

### 4. 关键配置
* **`stop-writes-on-bgsave-error`**：默认 `yes`。当后台快照生成失败（如磁盘空间满）时，Redis 会立刻拒绝新的写入请求，以此来强行警告开发者，保障数据一致性。推荐保持开启。

### 5. RDB 的优缺点
* **🟢 优势：**
  1. 适合大规模的数据恢复（如异地冷备）。
  2. 生成的二进制文件极其紧凑，节省磁盘空间。
  3. 恢复速度极快，远超 AOF。
  4. 极大化 Redis 性能，主进程不参与 I/O。
* **🔴 劣势：**
  1. **数据丢失风险高：** 备份是在一定时间间隔（如 5 分钟）做一次，如果 Redis 意外宕机，会**丢失最后一次快照后的所有修改**。
  2. **内存膨胀与 CPU 消耗：** `fork` 子进程时，虽然利用了写时复制（Copy-On-Write, COW）技术，但在极端高并发写的情况下，仍需考虑大致 2 倍的内存膨胀风险，且处理海量数据时依然消耗 CPU 性能。

## 二、 AOF 持久化 (Append Only File)

### 1. 核心概念
以独立日志的方式记录每次写命令，重启时再重新执行 AOF 文件中的命令来恢复数据。
* **机制：** 只许追加（Append）文件，不可改写文件。Redis 启动时会从前到后逐一执行指令完成数据重建。
* **配置：** 默认不开启。可通过配置 `appendonly yes` 开启，文件名为 `appendonly.aof`。
* **⚠️ 优先级机制：** 当 AOF 和 RDB 同时开启时，系统**默认取 AOF 的数据**进行恢复，因为 AOF 的数据通常更完整。

### 2. 同步规则 (Sync Strategy)
在 `redis.conf` 中通过 `appendfsync` 配置：
* **`always` (始终同步)：** 每次写入都会立刻记入日志。数据绝对安全，但严重拖慢 Redis 性能。
* **`everysec` (每秒同步) 【默认且推荐】：** 每秒强制刷盘一次。兼顾性能与安全，最多只丢失 1 秒的数据。
* **`no` (操作系统决定)：** Redis 不主动同步，完全依赖操作系统的缓存刷盘机制，不可控。

---

### 3. AOF 重写机制 (ReWrite)
由于 AOF 是不断追加的流水账日志，文件会越来越庞大。为了避免磁盘塞满和恢复过慢，Redis 引入了重写机制（瘦身），**只保留可以恢复当前数据的最小指令集**。

**(1) 何时触发重写？**
* **手动触发：** 客户端发送 `BGREWRITEAOF` 命令。
* **自动触发（基于配置文件）：**
  * `auto-aof-rewrite-percentage 100`：AOF 文件大小比上次重写后增长了 100%。
  * `auto-aof-rewrite-min-size 64mb`：且当前 AOF 文件大小必须大于 64MB 时，才会触发。

**(2) 重写工作流程 (核心补充)**
1. **Fork 子进程：** 主进程 `fork` 出一个 `bgrewriteaof` 子进程。
2. **生成新AOF：** 子进程扫描当前内存中的数据，生成能够还原这些数据的全新指令集，写入到一个临时新的 AOF 文件中。*(注：Redis 4.0 以后默认开启混合持久化，此时子进程会先以 RDB 的二进制格式将当前内存数据写到新 AOF 文件的头部，这样体积更小)*
3. **主进程缓存增量：** 在子进程重写期间，主进程仍在接收客户端的写请求。主进程会将这些新请求**同时写入旧 AOF 缓冲区**（保障旧数据安全）和**AOF 重写缓冲区**（AOF Rewrite Buffer）。
4. **追加增量：** 子进程完成重写并通知主进程。主进程将“AOF 重写缓冲区”里的增量数据追加到新 AOF 文件的末尾。
5. **文件替换：** 原子性地用新 AOF 文件重命名并替换旧 AOF 文件，完成瘦身！

### 4. AOF 的优缺点
* **🟢 优势：**
  1. 备份机制更稳健，数据完整性极高（最多丢 1 秒数据）。
  2. 日志文件是可读的纯文本（未开启混合持久化时）。如果有人误操作执行了 `FLUSHALL`，只要赶在重写发生前，停机并删掉 AOF 文件末尾的那句 `FLUSHALL` 命令，重启即可完美抢救数据。
* **🔴 劣势：**
  1. 文件体积远大于 RDB，占用更多磁盘空间。
  2. 启动时的恢复（指令回放）速度远慢于 RDB。
  3. 频繁的磁盘 I/O（如 `always`）会带来显著的性能衰减。

## 三、 RDB 与 AOF 混合使用 (Redis 4.0+ 推荐架构)

在实际的企业级生产环境中，通常推荐**同时开启 RDB 和 AOF**（即混合持久化模式 `aof-use-rdb-preamble yes`）。

### 💡 两个都用的极致好处：
1. **数据安全性兜底（AOF 的功劳）：** 依靠 AOF 的 `everysec` 策略，哪怕服务器突然断电，最多也只会丢失 1 秒钟的数据，完美解决了 RDB 丢失数据过多的痛点。
2. **恢复速度与文件体积优化（RDB 的功劳）：** 在 AOF 触发重写时，Redis 会先将当前内存里的全量数据以 RDB 的紧凑格式写入 AOF 文件的头部，然后再将后续的增量操作以 AOF 文本格式追加在后面。这不仅大幅缩小了 AOF 文件的体积，还能在 Redis 重启时，利用 RDB 的极速加载能力瞬间恢复绝大部分数据，最后再回放少量的 AOF 增量日志，真正做到了“又快又稳”。
