# Redis 事务与并发控制核心笔记

## 一、 什么是 Redis 事务？
Redis 事务是一个单独的隔离操作。它的主要作用是**串联多个命令，防止别的命令插队**。
事务中的所有命令都会被序列化、按顺序地执行。在执行过程中，绝不会被其他客户端发来的请求所打断。

---

## 二、 事务的基础操作 (三步走)

* **`MULTI`**：开启事务。从输入此命令开始，后续输入的命令都会依次进入“命令队列”中，但不会立刻执行。
* **`EXEC`**：执行事务。Redis 会将队列中的命令依次真正执行。
* **`DISCARD`**：放弃事务。清空当前队列中的所有命令，退出事务状态。

---

## 三、 事务的错误处理机制 (极其重要)

Redis 对事务中的错误处理分为两种完全不同的情况：

### 1. 组队时错误 (入队报错，全体取消)
如果在 `MULTI` 之后，输入的命令本身存在语法错误（比如参数数量不对、命令拼写错误），Redis 会当场报错。那么在执行 `EXEC` 时，整个事务队列都会被取消，**所有命令都不执行**。

**【代码示例】**
```text
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379> set k1 v1
QUEUED
127.0.0.1:6379> set k2       # 语法错误：少了一个 value 参数
(error) ERR wrong number of arguments for 'set' command
127.0.0.1:6379> set k3 v3
QUEUED
127.0.0.1:6379> EXEC
(error) EXECABORT Transaction discarded because of previous errors. # 事务被强行打断，k1 和 k3 都没有被设置
```

### 2. 执行时错误 (运行时报错，只错自己，其他照常)
如果入队的命令语法都没问题（顺利返回 `QUEUED`），但在真正执行 `EXEC` 时，某条命令触发了逻辑错误（比如用 incr 去对一个字符串做自增），此时**报错的命令执行失败，但其他的命令会继续成功执行，绝对不会回滚！**

**【代码示例】**
```text
127.0.0.1:6379> set k1 "hello"   # k1 是一个字符串
OK
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379> incr k1          # 语法没问题，顺利入队
QUEUED
127.0.0.1:6379> set k2 v2        # 顺利入队
QUEUED
127.0.0.1:6379> EXEC
1) (error) ERR value is not an integer or out of range  # incr k1 失败了
2) OK                                                   # 但是 set k2 依然成功了！(无回滚机制)
```

## 四、 事务的冲突与锁机制

在高并发场景下，多个客户端同时操作同一个 Key，就会产生冲突。

### 1. 悲观锁 (Pessimistic Lock)
* **思想：** “总有刁民想害朕”。每次去拿数据时都认为别人会修改它。
* **做法：** 在拿数据之前先上锁。别人想拿数据就必须阻塞等待（Block），直到拿到锁。
* **应用：** 传统关系型数据库（如 MySQL 的行锁、表锁、读写锁）。

### 2. 乐观锁 (Optimistic Lock)
* **思想：** “世界还是美好的”。每次去拿数据时都认为别人不会修改它。
* **做法：** 不上锁。但在最终更新数据时，会去判断一下：在此期间有没有别人改过这个数据？（通常利用**版本号 Version** 机制来实现）。
* **应用：** 适用于“多读”的应用类型，能极大提高系统吞吐量。**Redis 就是利用这种 Check-and-Set (CAS) 机制来实现并发控制的。**

---

## 五、 使用 WATCH 实现 Redis 乐观锁

**`WATCH key [key ...]`**：在执行 `MULTI` 之前，先监视一个或多个 key。如果在事务 `EXEC` 执行之前，这些 key 被其他客户端改动了，那么当前事务将被立刻打断（执行失败，返回 nil）。

**【代码示例：模拟两个客户端抢票】**

**客户端 1 (Terminal A):**
```text
127.0.0.1:6379> set ticket 1     # 初始化，还剩 1 张票
OK
127.0.0.1:6379> WATCH ticket     # 开启乐观锁，盯住这张票
OK
127.0.0.1:6379> MULTI            # 开启事务
OK
127.0.0.1:6379> decr ticket      # 准备买票（入队）
QUEUED
```

**此时，客户端 2 (Terminal B) 突然插队买走了票：**
```text
127.0.0.1:6379> decr ticket      # 客户端2直接拿走了票，ticket 变成 0
(integer) 0
```

**客户端 1 (Terminal A) 继续提交事务：**
```text
127.0.0.1:6379> EXEC             # 客户端1尝试提交
(nil)                            # 返回 nil 代表事务执行失败！因为 WATCH 发现 ticket 被改过了。
```

## 六、 Redis 事务的三大特性总结

1. **单独的隔离操作：** 事务中的所有命令都会序列化、按顺序地执行。执行过程中不会被其他客户端发送来的命令插队打断。
2. **没有隔离级别的概念：** 队列中的命令在提交（EXEC）之前，都不会被实际执行。这就意味着不存在 MySQL 中那种“脏读”、“幻读”的复杂隔离级别概念。
3. **不保证原子性（重点）：** 事务中如果有一条命令在运行期执行失败，其后的命令仍然会被执行，**Redis 事务不支持回滚（Rollback）**。
