# Redis 主从复制 (Master-Slave Replication) 核心笔记

## 一、 核心概念
主从复制是指：当主机（Master）的数据发生更新后，根据配置和策略，自动地、异步地同步到备机（Slave）的机制。
* **主机 (Master)：** 专门负责数据的**写操作**（Write）。
* **备机 (Slave)：** 专门负责数据的**读操作**（Read）。（默认配置下，备机是**只读**的，拒绝外部的写入请求以保证数据不混乱）。

## 二、 主从复制的核心作用
1. **读写分离，性能扩展：** 绝大多数互联网业务都是“读多写少”。让主机专心处理高并发的写请求，把海量的读请求分担给多台从机，能极大突破 Redis 单机的性能瓶颈。
2. **容灾快速恢复：** 如果主机突然宕机，数据不会丢失，因为所有的从机都保留着完整的最新数据备份。系统可以迅速将其中一台从机“提拔”为新的主机，马上恢复业务。

## 三、 架构分类及核心思考
* **一主一从：** 最简单的备份架构。
* **一主多从：** 生产环境标配（通常是一主二从或更多），能有效防止单个从机挂掉后，大量的读请求无处安放。

### 💡 深度拷问：主从复制中，为什么主机只有一台？
这涉及到底层分布式系统中最核心的**“数据一致性”**问题：
如果允许有两台或多台主机同时接收用户的“写操作”，假设：
1. 用户 A 往主机1 发送命令 `set ticket 10`
2. 用户 B 往主机2 发送命令 `set ticket 20`
这两台主机同时把数据同步给下面的小弟，小弟们该听谁的？数据冲突该如何解决？这会导致极其复杂的“脑裂”和锁机制，严重拖垮 Redis 最引以为傲的“极速性能”。
**结论：为了保证绝对的数据一致性，且维持极高的读写性能，普通的主从架构必须是“单点写入（单主）”。** *(注：如果确实需要多点写入来应对海量数据，Redis 提供了另一种更高级的架构叫 Redis Cluster 切片集群，那是另一个维度的技术了)*。

## 四、 搭建实战：一主多从 (以 1 主 2 从为例)

### 方案 A：在传统物理机上搭建 (繁琐，易出错)
在同一台物理机上模拟集群，核心思想是：**复制多份配置文件，修改端口和路径，启动多个进程。**

1. **准备配置文件：** 复制 3 份 `redis.conf`，分别命名为 `redis6379.conf`, `redis6380.conf`, `redis6381.conf`。
2. **修改从机配置（最繁琐的一步）：** 打开 6380 和 6381 的配置文件，必须修改以下几项，防止与主机冲突：
   * `port 6380` （修改端口号）
   * `pidfile /var/run/redis_6380.pid` （修改进程文件名字）
   * `logfile "6380.log"` （修改日志文件名字）
   * `dbfilename dump6380.rdb` （修改持久化备份文件名字）
3. **建立主从关系：** 在 6380 和 6381 的配置文件底部，加上认大哥的命令：
   * `replicaof 127.0.0.1 6379`
   * `masterauth 123456` (如果主机有密码，必须配这个)
4. **分别启动进程：**
   * `redis-server redis6379.conf`
   * `redis-server redis6380.conf`
   * `redis-server redis6381.conf`

### 方案 B：在 Docker 中搭建 (极简，生产推荐)
借助容器的网络隔离特性，我们完全不需要修改那些繁琐的内部文件名，只需一行命令即可搞定。

1. **启动主机 (Master)：**
   ```bash
   docker run -d --name redis-master -p 6379:6379 redis redis-server --requirepass 123456
   ```
2. **获取主机内部 IP：**
   ```bash
   docker inspect -f '{{range.NetworkSettings.Networks}}{{.IPAddress}}{{end}}' redis-master
   ```
   *(假设获取到的 IP 是 `172.17.0.2`)*
3. **启动从机 1 (直接在命令行注入参数认大哥)：**
   ```bash
   docker run -d --name redis-slave1 -p 6380:6379 redis redis-server --replicaof 172.17.0.2 6379 --masterauth 123456
   ```
4. **启动从机 2：**
   ```bash
   docker run -d --name redis-slave2 -p 6381:6379 redis redis-server --replicaof 172.17.0.2 6379 --masterauth 123456
   ```
5. **验证：** 进入主机的 `redis-cli`，输入 `info replication`，看到 `connected_slaves:2` 即代表集群搭建成功！

## 五、 主从复制的原理与宕机应对

在主从架构中，节点意外挂掉是家常便饭。Redis 对于主机和从机挂掉有着完全不同的处理逻辑。

### 1. 如果从机 (Slave) 挂掉之后，会出现什么情况？
* **表象：** 挂掉的从机立刻停止工作，无法提供读取服务。但是**主机和其他从机完全不受影响**，整个系统依然可以正常读写。
* **重启恢复后：** 当这台从机重新启动后，它会立刻去寻找配置中的大哥（Master）。
* **同步原理 (非常智能)：**
  * 如果从机只是断开了很短的一小会儿，它重新连上主机后，会触发**增量复制 (Partial Resync)**：主机只把从机掉线期间错过的那几条命令发给它，瞬间就能补齐数据。
  * 如果从机断开太久，或者是一个全新的从机刚加入，它连上主机后，会触发**全量复制 (Full Sync)**：主机会在后台立刻生成一份 RDB 快照文件发送给从机，从机清空自己现有的数据，完整加载这份 RDB，然后再接收主机后续传来的新命令。

### 2. 如果主机 (Master) 挂掉之后，会出现什么情况？（极其危险）
* **表象：** 主机一旦宕机，整个集群**彻底丧失了写入数据的能力**（因为从机默认只读）。
* **从机的反应：** 从机会变成“无头苍蝇”，但它们**绝对不会自动推选自己当新大哥**。如果你在从机里敲 `info replication`，会看到 `master_link_status:down`。它们只会忠诚地在原地死等，直到原来的大哥复活。
* **重启恢复后：** 如果你重新启动了之前挂掉的主机容器，它依然是 Master，从机会立刻重新连接它并继续待命。*(⚠️ 警告：如果挂掉的主机没有开启持久化，它重启后是一个空的数据库，它会把“空”同步给所有从机，导致整个集群数据瞬间全毁！)*

### 3. 如何解决主机挂掉的危机？(手动干预)
如果主机真的烧毁了，再也起不来了怎么办？后端人员必须赶紧进行手动抢救：
1. 登录到其中一台数据最完整的从机。
2. 敲下终极造反命令：`replicaof no one` （老版本为 `slaveof no one`）。
3. 这台从机会立刻“翻身做主人”，从 Slave 变成 Master。
4. 登录其他剩余的从机，修改它们的配置，让它们去认这个新的 Master 做大哥。

## 六、 补充：主从复制的底层原理三部曲

当一个从机启动，第一次连接到主机时，背后发生了什么？

1. **第一阶段：建立连接与同步请求 (SYNC)**
   从机主动向主机发送一个 `psync`（或老版本的 `sync`）命令，请求同步数据。
2. **第二阶段：主机快照备份 (RDB)**
   主机收到请求后，立刻在后台执行 `BGSAVE` 命令，生成一个当前内存的 RDB 数据快照。同时，主机会开辟一个**缓冲区**，用来记录在生成快照这段时间里，外界又新写入进来的命令。
3. **第三阶段：数据发送与持续命令传播 (Propagate)**
   主机把 RDB 文件发给从机，从机加载完毕后。主机再把刚才**缓冲区**里积压的新命令也发给从机。之后，只要主机执行了一条写命令，就会立刻像流水线一样转发给从机，保持数据永久同步。

## 七、 Redis 薪火相传与反客为主

在 Redis 的集群架构中，为了应对不同的业务场景（如超高并发读、异地容灾等），除了基础的一主多从，还有更灵活的拓扑结构。

---

### 1. 薪火相传 (Cascading Replication)

**核心定义：** “上一个 Slave 可以是下一个 Slave 的 Master”。从节点不仅同步主节点的数据，还可以接受其他从节点的连接请求。数据像接力棒一样在链条上传递：`Master -> Slave A -> Slave B`。



#### 🚀 优势：去中心化
* **减轻主节点压力：** 在传统的星型结构中，主节点必须为每个从节点单独推送数据。在薪火相传模式下，主节点只需同步给一个“二级代理”，大大节省了主节点的 CPU 和带宽。
* **分级管理：** 适合大规模集群，可以按机架或按区域设置中继节点。

#### ⚠️ 劣势：风险传递
* **链条脆弱性：** 如果中间的一台从机（中间商）挂掉，它下方的所有“下游节点”都将无法获取最新的数据同步。
* **数据延迟：** 每增加一个层级，数据同步到最末端的时间就会增加（物理延迟累加）。

---

### 2. 反客为主 (Promote Slave to Master)

**核心场景：** 当主节点（Master）因为断网、硬件故障或崩溃而宕机时，整个系统会失去“写入”能力。此时需要手动将一台从机提拔为新的主机。

#### 🛠️ 操作实现
1. **停止同步：** 在选中的从节点上执行 `replicaof no one`（老版本为 `slaveof no one`）。
2. **身份转变：** 该节点会立刻斩断与原主机的联系，并将自己升级为 Master，开始接收写请求。
3. **重组集群：** 运维人员需要手动修改其他从节点的配置，让它们执行 `replicaof <新主IP> <新主端口>` 重新归队。

#### 📝 总结与思考
* **手动弊端：** 这种手动操作方式响应慢、易出错，且不适合自动化程度高的生产环境。
* **未来之路：** 为了实现“无人值守”的自动切换，我们需要引入 **Redis Sentinel (哨兵模式)**，它能自动完成监控、选主和通知的全流程。

---

> **实验小贴士：** > 在 Docker 环境下，可以通过 `docker stop redis-master` 模拟主机宕机，然后观察 `redis-slave1` 的日志，体会“群龙无首”的状态。

## 八、 哨兵模式 (Sentinel)

### 1. 核心概念
哨兵模式是 Redis 的高可用解决方案。它是一个特殊的模式，Redis 哨兵是一个独立的进程，能够后台监控主机是否故障，如果发生故障能够**自动**将从节点转换为主节点，实现故障转移（Failover）。



---

### 2. 哨兵选举策略 (如何挑选新皇帝？)
当主机宕机后，哨兵会根据以下优先级顺序在从节点中选出新的 Master：

1.  **选择优先级靠前的：** 检查 `redis.conf` 中的 `replica-priority`（或 `slave-priority`）配置，数字越小优先级越高（默认 100）。
2.  **选择偏移量（Offset）最大的：** 偏移量是指从节点从原主机同步数据的数据量。偏移量越大，说明该从节点的数据最接近原主机，数据最全。
3.  **选择 RunID 最小的：** 每个 Redis 实例启动后都会随机生成一个 40 位的 `runid`。如果前两项都一样，则随机挑选 RunID 最小的服务。

**⚠️ 结果：** 选出新主后，哨兵会执行 `replicaof no one` 提拔它，并通知其他从机改认新主。**当挂掉的原主节点重新启动后，它会自动变成新主节点的从节点。**

---

### 3. 物理机搭建步骤 (Linux 环境)

1.  **创建配置文件：** 在 Redis 安装目录新建 `sentinel.conf`。
    ```bash
    vim sentinel.conf
    ```
2.  **编写核心配置：**
    ```conf
    # sentinel monitor <自定义名称> <主节点IP> <主节点端口> <通过票数>
    # 这里的 1 表示只要有 1 个哨兵认为主节点挂了，就进行切换
    sentinel monitor mymaster 127.0.0.1 6379 1
    ```
3.  **启动哨兵：**
    ```bash
    redis-sentinel sentinel.conf
    ```

---

### 4. Docker 搭建步骤 (容器化环境)

在 Docker 中，最快速的方式是直接进入容器或挂载配置文件。

#### 方案 A：快速进入容器配置
1.  **进入其中一个从机容器：**
    ```bash
    docker exec -it redis-slave1 bash
    ```
2.  **创建并配置哨兵文件：**
    ```bash
    cat <<EOF > /etc/redis/sentinel.conf
    sentinel monitor mymaster 172.17.0.3 6379 1
    sentinel down-after-milliseconds mymaster 3000
    EOF
    ```
3.  **运行哨兵进程：**
    ```bash
    redis-sentinel /etc/redis/sentinel.conf
    ```

#### 方案 B：使用 Docker Compose (推荐)
在实际开发中，通常会写一个 `docker-compose.yml` 同时启动 Redis 和 Sentinel 镜像，并在 `command` 中指定 `--sentinel` 参数。

---

### 5. 故障恢复演示
1.  **杀死主机：** `docker stop redis-master`
2.  **观察哨兵日志：** 你会看到 `+sdown`（主观下线） -> `+odown`（客观下线） -> `+try-failover`（开始切换） -> `+promoted-slave`（提升从机）。
3.  **重启原主机：** `docker start redis-master`
4.  **查看状态：** 进入原主机敲 `info replication`，你会发现它的角色已经变成了 `slave`。
