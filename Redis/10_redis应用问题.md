# Redis 核心高频面试题：缓存三大问题与分布式锁

在实际的高并发生产环境中，引入 Redis 缓存虽然极大地提升了读取性能，但也随之带来了经典的“缓存三大问题”以及集群环境下的并发控制需求。

---

## 一、 缓存穿透 (Cache Penetration)

**1. 问题描述**
查询一个**在数据库中根本不存在的数据**。每次针对此 Key 的请求，在缓存中获取不到（未命中），出于容错考虑又不会将空结果写入缓存，导致这些请求全部穿透缓存，直接压到后端数据库上。
*极端场景：* 若黑客利用此漏洞，发起大量带有不存在的 ID 的请求进行恶意攻击，可能瞬间压垮数据库。

**2. 解决方案**
* **① 缓存空值 (Cache Null Value)：**
  如果一个查询返回的数据为空，我们仍然把这个“空结果”进行缓存。为了防止占用过多内存或数据不一致，这类空结果的过期时间（TTL）会设置得很短，最长不超过 5 分钟。
* **② 设置可访问白名单 (Bitmaps)：**
  使用 Bitmaps 类型定义一个可以访问的有效名单。将名单 ID 作为 Bitmaps 的偏移量，每次访问时先和 Bitmaps 里的 ID 进行比对，如果访问的 ID 不在里面，直接在 Redis 层拦截，不允许访问数据库。
* **③ 布隆过滤器 (Bloom Filter)：**
  将所有可能存在的数据哈希到一个足够大的 Bitmaps 中。布隆过滤器空间效率和查询时间极佳。一个一定不存在的数据会被过滤器迅速拦截，从而避免对底层数据库的查询压力。*(注：存在一定的误判率且删除元素困难)*。
* **④ 实时监控与黑名单：**
  当发现 Redis 的命中率开始急速降低时，配合运维排查访问对象和访问的数据特征，对于恶意的 IP 或请求参数设置黑名单限制访问。

## 二、 缓存击穿 (Cache Breakdown)

**1. 问题描述**
某个极其热门的 Key 对应的数据存在，但**在 Redis 中恰好到了过期时间**。就在这一瞬间，有海量的并发请求涌来。这些请求发现缓存失效，会同时去抢着读取后端数据库并试图回设到缓存，这种大并发请求可能会瞬间把后端 DB 压垮。
*一句话总结：* **单点**热 key 过期导致的瞬间高并发暴击。

**2. 解决方案**
* **① 预先设置热门数据 (预热)：**
  在预知的高峰访问（如双11秒杀）来临前，人工或通过脚本提前把热门数据存入 Redis，并大幅延长这些热门 Key 的过期时长，甚至设为不过期。
* **② 实时调整 TTL：**
  现场监控哪些数据处于持续热门状态，动态调整和延长其 Key 的过期时长。
* **③ 使用互斥锁 (Mutex Lock)：**
  在缓存失效时，不要让所有线程立刻去 load DB。而是先让这些线程去争抢一个基于 Redis 的互斥锁（如 `SETNX`）。
  * **抢锁成功：** 负责去后端 load DB，更新缓存，最后释放锁。
  * **抢锁失败：** 证明已经有其他线程正在 load DB，当前线程只需休眠一小段时间（如 100ms）后，重新尝试获取缓存数据即可。

## 三、 缓存雪崩 (Cache Avalanche)

**1. 问题描述**
与缓存击穿类似，但规模更大。缓存雪崩是指**大量的 Key 在同一时间集体过期**（或者 Redis 服务直接宕机），导致原本应该由 Redis 挡住的海量并发请求，像雪崩一样全部直接落到了底层关系型数据库上。
*区别：* 击穿是针对“某一个”热 Key；雪崩是针对“大量/所有” Key。

**2. 解决方案**
* **① 打散过期时间 (最常用)：**
  在给缓存设置失效时间时，在原有的基础 TTL 上增加一个随机值（比如 1~5 分钟的随机数）。这样就能大幅降低各个缓存过期时间的重复率，极难引发集体同时失效的惨剧。
* **② 构建多级缓存架构：**
  采用 Nginx 本地缓存 + Redis 分布式缓存 + 应用程序本地缓存（如 Ehcache/Caffeine）的多层防线。
* **③ 限流与降级 (加锁/队列)：**
  用加锁或者队列的方式来限制对数据库发起读写请求的线程总数。当流量过大时，对部分非核心业务进行服务降级（直接返回友好提示），保护底层系统。*(注：严重影响并发性能，为保底策略)*。
* **④ 后台线程异步更新：**
  记录缓存数据是否快要过期（设置逻辑提前量），如果发现即将过期，不让业务线程去更新，而是触发通知给专门的后台异步线程，由它去数据库抓取最新数据并刷新缓存的 TTL。

## 四、 分布式锁的实现 (基于 Redis)

**1. 为什么需要分布式锁？**
原单体单机部署的系统演化成分布式集群后，程序运行在不同的机器和 JVM 进程上。传统的 Java API（如 `synchronized` 或 `ReentrantLock`）只能控制单个 JVM 内的并发，无法提供跨 JVM 的互斥能力。为了控制多台机器对共享资源的并发访问，必须引入第三方的跨 JVM 互斥机制。

**2. 分布式锁主流实现方案**
* **基于数据库实现：** 依靠数据库的唯一索引或排他锁（性能较差，极少使用）。
* **基于缓存 (Redis)：** 依靠 `SETNX` 等机制（**性能最高**，互联网大厂标配）。
* **基于 Zookeeper：** 依靠临时顺序节点机制（**可靠性最高**，但不适合超高并发场景）。

**3. 基于 Redis 实现分布式锁的核心命令**

* **上锁 (独占互斥)：**
  利用只有 Key 不存在时才能设置成功的特性。
  ```bash
  setnx user 10
  ```
* **释放锁：**
  业务执行完毕后，删除 Key，让其他线程可以继续争抢。
  ```bash
  del user
  ```
* **防死锁 (设置超时)：**
  为了防止拿到锁的机器突然崩溃导致锁永远无法释放（死锁），必须给锁加上过期时间。
  ```bash
  expire user 20
  ```
* **终极完美方案 (保证原子性)：**
  在早期的 Redis 版本中，`setnx` 和 `expire` 是分两步执行的，如果在两步中间发生宕机依然会死锁。现在的 Redis 支持在同一条命令中同时完成上锁和设置超时，保证了绝对的**原子性**。
  ```bash
  # NX = Not eXists (不存在才设置), EX = EXpire (单位:秒)
  set user 10 nx ex 20
  ```
