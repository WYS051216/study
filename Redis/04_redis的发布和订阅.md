# Redis 发布订阅模式 (Pub/Sub)

## 一、 核心概念
Redis 发布订阅（Pub/Sub）是一种**消息通信模式**。
在这种模式下，消息的发送者和接收者解耦：
* **发布者 (Publisher)**：负责发送消息。发布者不知道谁会接收消息，只管把消息扔进一个特定的“频道”。
* **订阅者 (Subscriber)**：负责接收消息。一个客户端可以同时订阅任意数量的频道。

## 二、 工作流程 (两步走)
1. **订阅频道**：客户端 (Sub) 提前关注某个具体的频道 (Channel)。此时该客户端进入阻塞/监听状态，等待消息到达。
2. **发布消息**：当发送者 (Pub) 向该频道发布一条消息后，Redis 服务器会立刻将这条消息推送给所有订阅了该频道的客户端。

## 三、 常用基础命令

### 1. 订阅频道 (消费者端)
```text
subscribe <channel> [channel ...]
```
* **示例：** `subscribe cctv1` （订阅 cctv1 频道）
* **注意：** 客户端一旦执行了订阅命令，就会进入监听状态，此时它只能接收后续的订阅相关命令，不能再执行普通的 `set`/`get` 操作。

### 2. 发布消息 (生产者端)
```text
publish <channel> <message>
```
* **示例：** `publish cctv1 "Tonight News"`
* **返回值：** 返回接收到这条消息的订阅者数量。

### 3. 【补充】模式匹配订阅 (高级玩法)
如果你想一次性订阅多个名字相似的频道，可以使用通配符：
```text
psubscribe <pattern> [pattern ...]
```
* **示例：** `psubscribe cctv*` （同时订阅 cctv1, cctv2, cctv5 等所有以 cctv 开头的频道）。

---

## ⚠️ 后端架构视角的“避坑指南”
在实际的企业级项目设计中，**一定要区分 Redis 的 Pub/Sub 和真正的专业消息队列（如 Kafka, RabbitMQ）！**

* **Redis Pub/Sub 是“阅后即焚” (Fire and Forget) 的：** 它没有任何消息持久化机制。如果发布者发消息时，某个订阅者刚好网络断开离线了，等它重新连上时，**刚才错过的消息就永远丢失了**。
* **适用场景：** 适用于即时聊天室、实时广播、系统内缓存实时刷新通知等**允许极少量消息丢失、追求极速**的场景。
* **不适用场景：** 绝对不能用于订单处理、支付扣款等**严禁丢数据**的核心业务（这类业务请老老实实用 Kafka 或 Redis 5.0 推出的 Stream 数据类型）。
