# Redis Cluster (切片集群)

## 一、 为什么需要 Redis 集群？(痛点分析)
在之前的主从模式、薪火相传模式以及哨兵模式中，虽然解决了一定程度的高可用问题，但依然存在两个致命痛点：
1. **IP 漂移问题：** 主机宕机后，虽然哨兵能选出新主机，但导致主节点的 IP 地址发生变化。此时，应用程序（后端代码）中配置的 Redis 连接池需要动态修改对应的主机地址和端口等信息，非常麻烦。
2. **海量数据瓶颈：** 写操作全部由单一的 Master 承担，无法突破单台机器的内存和网卡上限。

---

## 二、 Redis 集群的核心特点
为了解决上述问题，Redis 集群实现了对 Redis 的**水平扩容**和**去中心化**。

1. **水平扩容 (分摊数据)：** 启动 N 个 Redis 节点，将整个数据库分布存储在这 N 个节点中，每个节点存储总数据的 `1/N`。这打破了单机内存的限制。
2. **分区高可用性：** Redis 集群通过分区来提供一定程度的可用性：即使集群中有一部分节点失效或者无法进行通讯，集群也可以继续处理命令请求（自带类似哨兵的自动故障转移机制）。
3. **哈希槽路由 (Hash Slot)：** 集群固定拥有 16384 个哈希槽。客户端存取数据时，通过 `CRC16(key) % 16384` 算出槽位，集群会自动重定向（MOVED）到负责该槽位的真实机器 IP 上，应用层不再需要关心具体哪个 IP 是主节点。

---

## 三、 Redis 集群搭建实战 (要求：至少 3主3从，共 6 个节点)

### 方案 A：在物理机上搭建 (Linux)

#### 1. 准备 6 份配置文件
新建 6 个目录，准备 6 份 `redis.conf`。关键必须开启集群相关配置：
```conf
# 端口设置 (例如 6379 到 6384)
port 6379  
# 开启集群模式 (最重要)
cluster-enabled yes
# 集群节点信息配置文件 (自动生成，不用管内容，只要名字不同即可)
cluster-config-file nodes-6379.conf
# 节点超时时间 (毫秒)
cluster-node-timeout 5000
# 开启后台运行
daemonize yes
```

#### 2. 启动 6 个独立的 Redis 实例
```bash
redis-server redis-6379.conf
redis-server redis-6380.conf
# ... 依次启动 6 个
```
此时它们只是 6 个开启了集群功能的“散沙”，互相还不认识。

#### 3. 将节点组建为集群 (构建命令)
使用 `redis-cli` 的 `--cluster` 参数把这 6 个实例捏合在一起。
```bash
# --cluster-replicas 1 表示为每个主节点分配 1 个从节点
redis-cli --cluster create 127.0.0.1:6379 127.0.0.1:6380 127.0.0.1:6381 127.0.0.1:6382 127.0.0.1:6383 127.0.0.1:6384 --cluster-replicas 1
```
输入 `yes` 确认分配方案，集群搭建完毕。

---

### 方案 B：在 Docker 中搭建 (极简推荐)

在 Docker 中搭建集群需要解决容器互相通信的 IP 问题，必须创建一个专属的 Docker 网络。

#### 1. 创建专属 Docker 网络
```bash
docker network create redis-cluster-net
```

#### 2. 一口气启动 6 个集群节点容器
通过 Shell 循环脚本，瞬间启动 6 个配置好集群参数的容器（端口映射为 6371~6376）：
```bash
for port in `seq 6371 6376`; do \
  docker run -d -ti -p ${port}:6379 -p 1${port}:16379 \
  --name redis-${port} \
  --net redis-cluster-net \
  redis redis-server --cluster-enabled yes --cluster-config-file nodes.conf --cluster-node-timeout 5000; \
done
```
*(注：集群不但需要 6379 提供服务，还需要 16379 端口供节点之间互相发送 Gossip 协议进行通信)*

#### 3. 获取所有容器的内部 IP
```bash
docker inspect -f '{{.Name}} - {{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' $(docker ps -aq)
```
记录下这 6 个容器分配到的内部 IP（例如 `172.18.0.2` 到 `172.18.0.7`）。

#### 4. 执行集群合并命令
进入任意一个容器内部：
```bash
docker exec -it redis-6371 bash
```
在容器内部执行构建命令（填入刚才查到的 6 个 IP）：
```bash
redis-cli --cluster create 172.18.0.2:6379 172.18.0.3:6379 172.18.0.4:6379 172.18.0.5:6379 172.18.0.6:6379 172.18.0.7:6379 --cluster-replicas 1
```

## 四、 验证与使用技巧
* **连接集群：** 必须使用带有 `-c`（cluster）参数的命令行去连接，否则遇到跨槽位的数据会被拒绝！
  ```bash
  redis-cli -p 6371 -c
  ```
* **查看集群信息：** 成功连接后，输入以下命令查看集群健康度和槽位分配：
  * `cluster info` (查看集群整体状态)
  * `cluster nodes` (查看所有 6 个主从节点的具体分布和 ID)

## 五、 Redis 集群操作的原理

Redis Cluster 是典型的分布式系统，其核心设计思想围绕着“分布式共识”、“数据分区”以及“容灾高可用”展开。

---

### 1. Redis 集群的底层细节

* **最少节点限制：** 一个可以独立进行故障转移的 Redis 集群**至少需要三个主节点 (Master)**。
* **客观下线判定（过半机制）：** 集群中没有任何中心管理节点，节点间通过 Gossip 协议互相通信。当一个节点 A 出现网络故障时，其他主节点会对其进行投票。**只有当半数以上的主节点都认为该节点挂掉了**，集群才会将该节点判定为“客观下线（FAIL）”，并触发后续的自动故障转移。
* **高可用交叉分布原则：** * 生产环境下，三台主节点应尽量分配在**不同的物理 IP 地址（不同服务器）**上，防止单台物理机断电导致全盘瓦解。
  * **核心铁律：** 任何一个节点的从库（Slave）绝对不能和它的主库（Master）部署在同一个 IP 地址上。必须交叉部署，确保某台机器挂掉时，异地的从库能够站出来接管数据。

---

### 2. 哈希槽 (Slots) 分配机制

* **插槽总量：** 一个 Redis 集群固定的包含 **16384** 个哈希槽（Slots）。数据库中的每一个键（Key）都通过算法精准地绑定在其中一个插槽上。
* **路由算法：** 集群使用公式 `CRC16(key) % 16384` 来计算键属于哪个槽。集群中的每个主节点负责处理其中一部分插槽（例如：Node A 负责 0~5460，Node B 负责 5461~10922 ...）。
* **多键操作限制（CROSSSLOT 错误）：** * 如果多个键不在同一个 slot 下，集群模式下是**不能**使用 `MGET`、`MSET` 等多键原子操作的。
  * **完美解法 —— 组（Hash Tag）概念：** 我们可以通过 `{}` 来强制定义组。当 Redis 发现 Key 中包含 `{}` 时，**它只会对 `{}` 内部的字符串进行哈希计算**。
  * *示例：* `{user}:age` 和 `{user}:name` 虽然完整名字不同，但因为 `{}` 内都是 `user`，计算出的哈希槽绝对一模一样，从而被强行分配到同一个节点上，完美支持 `MGET` 操作。

---

### 3. 查询集群中的值与槽位

在集群模式下，可以通过专有命令查看某个 Key 对应的插槽归属：
```bash
# 查询键 k2 属于 16384 个插槽中的哪一个
cluster keyslot k2
```
*注：在连接集群时，务必使用 `redis-cli -c` 启动集群模式，这样当查询的键不在当前节点时，终端会自动进行 `MOVED` 重定向跳转，无需人工干预。*

---

### 4. Redis 集群的灾难故障恢复

**核心拷问：** 如果极端灾难发生，**所有负责某一段插槽的主节点和从节点全都宕机了**（例如负责 0~5460 槽位的 Master 和 Slave 同时烧毁），Redis 服务是否还能继续？

这完全取决于 `redis.conf` 中的核心配置参数：`cluster-require-full-coverage`

#### 策略 A：`cluster-require-full-coverage yes`（默认值 - 严谨一致型）
* **结果：** **整个集群全部挂掉，直接拒绝所有服务。**
* **原理：** 架构设计认为，16384 个槽位必须 100% 都在线才叫完整的数据库（Full Coverage）。只要有一段插槽缺失，说明部分数据已经失联，为了防止数据不一致或产生脏数据，Redis 宁可选择全盘罢工（抛出 FAIL 错误）。

#### 策略 B：`cluster-require-full-coverage no`（高可用营业型）
* **结果：** **部分瘫痪，其余完好的插槽继续正常营业。**
* **原理：** 尽管死掉的那段插槽对应的数据全部无法读取也无法存储，但集群中其他未受影响的主节点（负责其他槽位的机器）依然可以正常响应客户端的读写请求。尽最大努力保证系统的**分区可用性**。

---

### 💡 自动复活行为
无论采用上述哪种策略，当那台**挂掉的原主节点被修复并重新启动之后，它会向集群认错认输，自动变成新主节点的从节点（Slave）**，重新同步数据归队，集群恢复满血状态。
